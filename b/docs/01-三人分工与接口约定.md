# Tree of Life · 三人分工与接口约定

## 1. 协作原则

三个人共同完成同一个游戏。每个人及其 Agent 只实现自己负责的模块，并通过已经约定的头文件交互。

- 游戏逻辑模块不得包含 `raylib.h`。
- UI 不直接修改资源、物种、突变、EP 或永久等级，只提交操作请求。
- 物种、突变、环境和强化的编号由统一枚举或数据表管理。
- 平衡数值只保存在一个数据源中，界面和结算模块不得复制公式。
- 共享结构体和函数签名发生变化时，三人先更新文档并共同确认。
- Agent 不得因为实现方便而增加资源、删除机制或改变所有权。

## 2. 三人职责

### Member A · Core Engine

负责游戏核心引擎、资源经济、单轮推进和存档。

具体任务包括：

- `GameState` 初始化和状态切换。
- 固定时间步和游戏主循环中的逻辑更新。
- ATP、Biomass、DNA 的生产、消费和边界检查。
- 点击收益和三类单轮基础升级。
- 各活跃物种产出的汇总。
- 新轮重置，同时保留 `LegacyState` 和永久图鉴。
- 保存、读取、版本检查和防止重复领取 EP。
- 提供不依赖 Raylib 的控制台测试入口。

主要文件：

```text
src/game.c
src/economy.c
src/save.c
include/game.h
include/economy.h
include/save.h
```

### Member B · Evolution & Progression

负责物种、突变、环境自然选择、纪元结算和永久成长。

具体任务包括：

- 物种数据、阶段和进化树前置条件。
- 任一活跃物种槽的分化、额外物种槽和物种图鉴发现。
- 突变池、候选生成、稀有权重和突变应用。
- 环境事件选择、适应度、种群变化和危机统计。
- EP 公式、结算明细和重复里程碑保护。
- 四条永久路线、升级成本和效果计算。
- 为 A 提供每个物种的最终产率与种群变化结果。
- 为 C 提供名称、说明、前置条件和当前效果数据。

主要文件：

```text
src/evolution.c
src/species.c
src/environment.c
src/prestige.c
src/legacy.c
include/evolution.h
include/environment.h
include/legacy.h
```

### Member C · Raylib & UX

负责 Raylib 图形界面、输入、反馈和资源文件。

具体任务包括：

- Raylib 初始化、主窗口和帧循环。
- 主游戏页面、进化树、物种面板和环境提示。
- 突变候选和分化选择交互。
- End of Era 预览与确认页面。
- Evolution Legacy 加点页面。
- Codex、历史最佳和成就显示。
- 按钮状态、提示文本、动画、音效和窗口适配。
- 将玩家输入转换为统一 `GameAction`，显示 `ActionResult`。

主要文件：

```text
src/main.c
src/ui.c
src/render.c
src/screens.c
src/input.c
include/ui.h
assets/
```

## 3. 模块依赖

```text
Raylib 输入
    ↓
Member C · UI / Input
    ↓  GameAction
Member A · Game Facade / Economy / Save
    ↓  调用规则
Member B · Evolution / Environment / Legacy
    ↓  返回计算结果
Member A · 提交状态变化
    ↓  只读 GameState
Member C · Render
```

C 只能通过公共接口提交操作。B 负责规则和计算，A 负责协调调用和一次性提交状态，避免多个模块同时修改同一字段。

## 5. 共享数据结构

以下是接口草案。编码开始前由三人一起确认，随后写入 `game_types.h`。字段名称可以在评审时微调，含义和所有权不能改变。

```c
#ifndef GAME_TYPES_H
#define GAME_TYPES_H

#include <stdbool.h>

#define MAX_ACTIVE_SPECIES 3
#define MAX_SPECIES 32
#define MAX_MUTATIONS 64
#define MAX_ENVIRONMENTS 16
#define MAX_MUTATION_CHOICES 4

typedef enum {
    PHASE_RUNNING,
    PHASE_END_ERA_PREVIEW,
    PHASE_LEGACY
} GamePhase;

typedef enum {
    UPGRADE_METABOLISM,
    UPGRADE_REPRODUCTION,
    UPGRADE_GENOME
} RunUpgradeType;

typedef enum {
    LEGACY_METABOLISM,
    LEGACY_MUTATION,
    LEGACY_ADAPTATION,
    LEGACY_DIVERSIFICATION
} LegacyBranch;

typedef enum {
    ACTION_CLICK_ATP,
    ACTION_BUY_RUN_UPGRADE,
    ACTION_GENERATE_MUTATION_OFFER,
    ACTION_CHOOSE_MUTATION,
    ACTION_SPECIATE,
    ACTION_OPEN_END_ERA,
    ACTION_CANCEL_END_ERA,
    ACTION_CONFIRM_END_ERA,
    ACTION_BUY_LEGACY,
    ACTION_START_NEW_RUN,
    ACTION_BUY_SUB_UPGRADE
} ActionType;

typedef struct {
    int species_id;
    bool is_main_lineage;
    double population;
    bool mutations[MAX_MUTATIONS];
} SpeciesState;

typedef struct {
    bool active;
    int species_slot;
    int choice_count;
    int mutation_ids[MAX_MUTATION_CHOICES];
    double dna_costs[MAX_MUTATION_CHOICES];
} MutationOfferState;

typedef struct {
    double atp;
    double biomass;
    double dna;
    double knowledge;
    double elapsed_time;

    int era;
    int run_upgrade_levels[3];
    int active_species_count;
    SpeciesState active_species[MAX_ACTIVE_SPECIES];

    MutationOfferState mutation_offer;

    int current_environment_id;
    int next_environment_id;
    double environment_time_left;
    double event_interval_left;
    double crisis_start_population;
    bool adaptation_shield_used;
    bool adaptation_shield_active;

    unsigned int rng_state;

    bool discovered_species[MAX_SPECIES];
    bool discovered_mutations[MAX_MUTATIONS];
    bool survived_crises[MAX_ENVIRONMENTS];

    double max_biomass;
    int capacity_levels;
    int reserve_levels;
    int tech_levels[MAX_SPECIES];
    bool reward_claimed;
} RunState;

typedef struct {
    int evolution_points;
    int levels[4];

    bool codex_species[MAX_SPECIES];
    bool codex_mutations[MAX_MUTATIONS];

    int best_era;
    int best_evolution_points;
    double best_biomass;
} LegacyState;

typedef struct {
    int save_version;
    GamePhase phase;
    RunState run;
    LegacyState legacy;
} GameState;

typedef struct {
    ActionType type;
    int target_species_slot;
    int target_id;
    int option;
} GameAction;

typedef enum {
    ACTION_OK,
    ACTION_INVALID_PHASE,
    ACTION_INVALID_TARGET,
    ACTION_NOT_ENOUGH_ATP,
    ACTION_NOT_ENOUGH_BIOMASS,
    ACTION_NOT_ENOUGH_DNA,
    ACTION_NOT_ENOUGH_EP,
    ACTION_NOT_ENOUGH_KNOWLEDGE,
    ACTION_REQUIREMENT_NOT_MET,
    ACTION_LEVEL_MAXED,
    ACTION_ALREADY_CLAIMED
} ActionCode;

typedef struct {
    ActionCode code;
    double amount_spent;
    int affected_id;
} ActionResult;

typedef struct {
    int era_points;
    int mutation_points;
    int species_points;
    int crisis_points;
    int biomass_points;
    int total_points;
} EraReward;

typedef struct {
    double atp_per_second;
    double biomass_per_second;
    double dna_per_second;
    double knowledge_per_second;
    double population_delta_per_second;
    double environment_multiplier;
    double final_population_cap;
    bool synergy_active;
} SpeciesRates;

typedef struct {
    int current_environment_id;
    int next_environment_id;
    double environment_time_left;
    double event_interval_left;
    bool event_started;
    bool event_ended;
    bool crisis_survived;
    int ended_environment_id;
    double crisis_lowest_population;
} EnvironmentStep;

#endif
```

`SpeciesState` 中突变属于具体物种。`RunState` 中发现数组属于本轮统计。`LegacyState` 中图鉴数组跨轮保存。两者不能合并，否则新轮 EP 统计会错误地把旧发现再次计入。

`MutationOfferState` 和 `rng_state` 必须进入存档。`ACTION_GENERATE_MUTATION_OFFER` 只在当前没有有效候选时生成一次，反复打开页面返回同一组候选。选择成功、物种分化或开始新轮后再清除。`GameAction.option` 用于物种分化时选择是否保留亲本等附加选项。

物种分化时，`GameAction.target_species_slot` 指向发起分化的活跃槽，既可以是主谱系，也可以是已经解锁的额外分支；`option = 0` 表示后代原地替换该槽，另一槽（主谱系或额外分支）保持不变，`option = 1` 表示把本次亲本保留为额外分支——该选项只允许从主谱系发起，必要时替换旧额外分支。其他动作的 `option` 设为 0。

分化的前置校验始终针对发起槽的物种：亲本关系、必须突变、永久等级和 Biomass 成本都按该槽计算。额外分支分化不推进时代，`evolution_main_stage` 只读取主谱系槽。

## 6. 公共 API

### 6.1 A 提供的游戏入口

```c
void game_init(GameState *game);
void game_update(GameState *game, double dt);
ActionResult game_apply_action(GameState *game, GameAction action);
void game_start_new_run(GameState *game);
```

- `game_update` 只在 `PHASE_RUNNING` 推进模拟。
- `game_apply_action` 先检查，再执行。失败操作不得扣除任何资源或只修改一半状态。
- C 不直接调用 B 的修改函数，由 A 的入口统一协调。

### 6.2 B 提供的进化规则

```c
MutationOfferState evolution_generate_mutation_offer(
    const GameState *game,
    int species_slot
);

ActionCode evolution_validate_speciation(
    const GameState *game,
    int species_slot,
    int target_species_id
);

SpeciesRates evolution_calculate_species_rates(
    const GameState *game,
    int species_slot
);

EnvironmentStep environment_calculate_step(
    const GameState *game,
    double dt
);

EraReward prestige_preview_reward(const GameState *game);
ActionCode legacy_validate_upgrade(
    const GameState *game,
    LegacyBranch branch
);
```

`MutationOfferState` 包含候选编号、最终 DNA 价格和候选数量。`SpeciesRates` 包含该物种的四资源产率（含理念）、种群变化、环境倍率、种群上限和协同状态。`EnvironmentStep` 包含当前固定步内的环境计时、事件切换和危机统计结果。B 返回计算结果，A 负责一次性写入 `GameState`。具体计算见《02-数据与计算规则》并视为编码基准。

### 6.3 A 提供的存档接口

```c
typedef enum {
    SAVE_OK,
    SAVE_FILE_ERROR,
    SAVE_BAD_VERSION,
    SAVE_INVALID_DATA
} SaveResult;

SaveResult save_write(const char *path, const GameState *game);
SaveResult save_read(const char *path, GameState *out_game);
```

读档必须先读入临时变量并完成版本、数组数量、编号、资源非负值和阶段检查，再替换当前状态。

### 6.4 C 提供的界面入口

```c
void ui_init(void);
void ui_update(const GameState *game, GameAction *pending_action);
void ui_render(const GameState *game, const ActionResult *last_result);
void ui_shutdown(void);
```

UI 收到 `const GameState *`，不能绕开动作接口修改游戏数据。

### 6.6 初始化与轮次契约

1. `game_init` 先写 `RunState.rng_state`，再调用 `environment_init_run`；后者会消耗一次随机数。
2. 新轮顺序固定为：清零 `RunState` → 写 `rng_state` → 设置初始物种与资源 → `environment_init_run` → `legacy_apply_new_run_bonuses` → 进入 `PHASE_RUNNING`。
3. `discovered_species[SPECIES_PROTOCELL]` 与 `legacy.codex_species[SPECIES_PROTOCELL]` 由 A 在初始化和新轮时写入；B 的规则函数不代劳。
4. `run.era` 由 A 自增；`save_version` 由 A 写为 6（第十二轮新增阶段 11、Omega Point 与危机最低人口日志字段）；`highest_biomass_milestone` 已删除，里程碑统一由 `max_biomass` 派生。
5. 新轮与读档时必须把 `run.knowledge` 清零、`run.tech_levels` 整体置零、`run.crisis_min_population` 置零；理念与危机最低人口只在本轮有效，不跨轮保存。

## 7. 每帧数据流

采用固定模拟步长，例如 0.1 秒。Raylib 帧率可以变化，核心模拟结果仍保持稳定。

```text
1. C 读取鼠标和键盘
2. C 生成零个或一个 GameAction
3. A 调用 game_apply_action
4. A 累积真实时间并按固定步长调用 game_update
5. game_update 向 B 查询物种产率和环境结果
6. A 一次性提交资源及种群变化
7. C 读取最终 GameState 并绘制
```

更新多个物种时，先用帧开始状态计算所有结果，再一起写回。不能先更新物种 0，再让物种 1 读取已经改变的资源，否则数组顺序会影响游戏结果。

## 8. 纪元状态流

```text
PHASE_RUNNING
  ├─ 打开预览 → PHASE_END_ERA_PREVIEW
  │                 ├─ 取消 → PHASE_RUNNING
  │                 └─ 确认 → 结算一次 EP → PHASE_LEGACY
  └─ 继续成长

PHASE_LEGACY
  ├─ 购买永久强化
  └─ 开始新轮 → 重置 RunState → PHASE_RUNNING
```

- End of Era 预览和 Legacy 阶段暂停单轮模拟。
- 确认结束时先生成一份 `EraReward`，再检查 `reward_claimed`，最后一次性入账。
- EP 入账和阶段切换必须在同一次状态提交中完成，并立即允许存档。
- 读档停留在 Legacy 页面时不能再次领取上一轮奖励。

## 9. Git 分支和合并

建议建立以下长期分支。

- `main` 保存随时可以演示的稳定版本。
- `develop` 用于三人集成。

每项任务建立短功能分支，例如：

```text
feat/a-economy
feat/a-save
feat/b-mutation
feat/b-environment
feat/c-main-screen
feat/c-legacy-screen
```

合并规则：

1. 共享头文件先单独评审并合入 `develop`。
2. 每个功能分支从最新 `develop` 创建。
3. 功能完成后由一名非作者成员审查。
4. 先合规则和数据，再合核心调用，最后合 UI 接入。
5. `develop` 完成共同验收后再合入 `main`。
6. 禁止三个人分别复制并修改 `game_types.h`。

公共接口的变更必须在同一次合并中更新声明、实现、调用方和本文档。

## 10. 并行开发办法

### A 的临时依赖

A 可以用固定的 `SpeciesRates` 假数据完成资源更新和控制台测试，等待 B 的真实计算接入。

### B 的临时依赖

B 用手工构造的 `GameState` 测试突变、环境、EP 和永久强化，不依赖 Raylib。

### C 的临时依赖

C 用一份固定示例 `GameState` 绘制页面和测试按钮，不在 UI 中实现临时经济公式。

三个人都可以并行工作，最后只替换模拟数据来源，不重写页面和规则。

## 11. 里程碑和验收

### M0 · 设计与接口冻结

- 三人读完两份文档。
- 确认结构体、枚举、函数签名和文件所有权。
- 建立仓库、`main`、`develop` 和基础目录。

验收结果是三个最小程序都能包含公共头文件并完成编译。

### M1 · 增量核心

- 点击获得 ATP。
- 三资源自动增长。
- 三类单轮升级可购买。
- Raylib 页面显示资源及每秒产速。

### M2 · 进化与选择

- 主谱系能够选择突变和物种分化；解锁第二槽后，额外分支同样可以选择突变和分化。
- 至少两个环境事件会对不同特征产生不同结果。
- 界面能够解释适应度变化来源。

### M3 · 额外分支

- `Diversification Lv.2` 解锁第二活跃物种槽。
- 两个物种独立拥有种群和突变。
- 额外分支可以独立分化：后代原地替换该槽，主谱系不受影响。
- `Diversification Lv.5` 把活跃物种槽扩展到 3 个；`MAX_ACTIVE_SPECIES = 3`，`RunState` 含容量与储备字段，存档版本升到 3。
- `Lv.3` 协同加成在数值和界面上都可见。

### M4 · Prestige 完整闭环

- 可以预览、取消和确认结束纪元。
- EP 明细与总数一致并且只入账一次。
- 四路加点会在新轮产生对应效果。
- 存读档不能重复领取奖励。

### M5 · 集成与展示

- 达到课程最终版内容数量。
- 主页面、进化树、结算、Legacy 和 Codex 可完整操作。
- 完成数值平衡、边界测试、README 和演示流程。
