## 0. 这份文档解决什么

### 0.1 一句话

把画面从

> **「一枚样本放在一张空白玻片上，其余是灰绿色的纸与线」**

改成

> **「一枚样本泡在培养液里，视野边缘还有别的东西——但你数不清有几只、也看不清它们长什么样」**

用户的原话是"生物科技感，神秘感，比如有细胞元素等生物背景的美化"。翻译成可执行的两条验收线：

| # | 要求 | 本文的对应判据 |
|---|---|---|
| U1 | 加了背景之后，**第一眼仍能读清所有数值** | §1.3 铁律 CR ≤ 1.25，用实测证明最弱文字仍守 4.5:1 |
| U2 | 不能是"纯色面板截图"，**必须有可辨识的细胞/微生物元素在背景层** | §2 五个母题 + §7.1 五句话截图描述 |

U1 与 U2 是互相拉扯的。本文的全部工作就是找到那条"再亮一点就抢戏、再暗一点就看不见"的线，并把它变成一个能写进 `assert` 的数字。

### 0.2 与 01 的关系（逐条，避免歧义）

| 01 的条款 | 本文的态度 |
|---|---|
| §1.2 P1 单光源（光从样本背后） | **加强**。背景细胞的可见度**只由"内壁环比内部亮"表达**，等于给每只背景细胞都加了一圈背光边缘。不得出现高光斑、不得出现方向性明暗 |
| §1.2 P2 圆是生命，直角是人造 | **严格遵守**。细胞/培养皿只用圆与环；测量网格与刻度标尺是**仪器**，按 P2 原文属于允许的直角品类 |
| §1.2 P3 静态即完整 | **严格遵守**。背景层不承载任何状态，动效只用来"让它不那么死"，删掉动效画面语义不变 |
| §2.2 token 表（现已扩到 **35 个**：16 原有 + 9 派生 + 7 物种 + 3 氛围） | **新增 3 个**（2 个背景层 + 1 个内容层），见 §5；不改任何既有 hex。已在 01 §2.2b 并入 |
| §2.5 分层最小 CR 1.10 | **反向利用**。背景新色与 `COL_BG` 的 CR 必须 **< 1.10**——即"单个 token 本身几乎看不见"，可见度全部来自多层叠加。见 §5.1 |
| §4.4 发光 ≤3 层 / 单层 α ≤0.10 / 总 α ≤0.18 | **不适用于背景层**（那条约束的对象是"发光"，是要抢戏的）。背景层用 §1.3 的 CR 铁律，数值上比 4.4 更严 |
| §7.2 R6 渐变 = 同心叠层 ≤3 层、α 步进 ≤0.04 | **直接复用**。暗角的 3 层就是这么来的（§4.1） |
| §7.3「本轮不做 R8」 | **已作废**。ENG-01 已实现 R8（120px 字体图集 + SS=3 画布），本文全部按"SS 可用"来写，并新增 §6.4「4K 加强项」说明现在多了什么自由度 |
| §8.3 禁止无限平移循环 | **严格执行**，并据此**回头修正现有代码**：`draw_stage()` 里 18 个 y 轴匀速上浮的气泡是无限平移循环，见 §6.5 |
| §9「不要动布局坐标」 | **严格遵守**。本文不移动任何一个卡片、按钮、文字 |

### 0.3 五条硬边界

| # | 边界 | 违反即作废 |
|---|---|---|
| B1 | 背景层永远画在**所有卡片之前**（z 序），且**不得进入任何卡片内部**（唯一例外：展台 `(396,166,524,300)`） | 一旦有背景元素画在文字之下但卡片之内，CR 计算的前提就崩了 |
| B2 | 背景层的任何参数不得读取 `ui_canvas_ss()` 参与布局/尺寸计算（01 §7.3 C1） | 只在 **init / resize 时**读一次 SS 用于分配 RenderTexture 尺寸，其余地方禁止 |
| B3 | 不引入 shader、不引入位图 | 若将来必须做真高斯模糊，标注"下一轮"，本轮用 §2.3 的同心圆模拟 |
| B4 | **禁止 `BeginScissorMode` / `EndScissorMode`，禁止 rlgl**。需要"裁到某个矩形内"时，一律改为**用几何解出可见部分**（角度区间、线段端点、或让帧缓冲边界自然裁掉） | SS>1 时 `BeginScissorMode` 的像素坐标会被 `Camera2D(zoom=SS)` 再放大一次 → 裁剪区错位（art-director 与 engineering-lead 交叉确认过的既有结论）。本工程的场景里**没有一处真的需要裁剪**：皿环用角度区间，网格用线段端点，边缘裁切细胞用帧缓冲边界 |
| B5 | **背景层不用任何 `*Lines` 系列原语**。判据不是"函数名带 Lines"，而是"**这条线最终是不是由 `glLineWidth` 画出来的**"（完整实测见**附录 Z**）。背景层要达到的效果**没有任何一处需要它**：描边一律用 **`DrawRing`（环）**、**`DrawLineEx`（线）** 或"填充形状相减" | 走 `rlBegin(RL_LINES)` 的原语**线宽以设备像素计、不吃 `Camera2D(zoom)`** → SS=3 恒为 1 物理像素，皿环变 1/3 粗细的**发丝环**。**FAIL 得极隐蔽**：线还在、颜色对、位置对，只是细了 2/3，SS=1 的开发窗口里完全正常。<br>⚠ **B5 是"背景层的自我约束"，不是全项目禁令**：附录 Z 实测 `DrawRectangleLinesEx(thick=1)`、`DrawPolyLinesEx(thick=1)` **是安全的**，`DrawRectangleRoundedLinesEx` 在 `thickness ∈ (1.0, 1.1666]` 也安全。写成通用禁令会与附录 Z 打架，也会逼人绕过它 |

## 1. 氛围分层模型

### 1.1 六层（对应你要的五层）

把「背景层」拆成两层（片基 / 悬液+刻度），因为它俩的**alpha 上限差 10 倍**，混在一起没法写判据。

| z | 层名 | 对应你的命名 | 画什么 | alpha 上限（单像素累计） | 可动 | 玩家能看清细节吗 |
|---|---|---|---|---|---|---|
| **L0** | 片基 `plate` | 最底 | **当前页底色**铺满（主界面 / Legacy = `COL_BG`；**End of Era = `COL_BG_DEEP`**）+ 2 层极淡的大尺度亮度起伏（模拟载玻片厚度不均） | **0.08** | 否 | 否（纯底噪） |
| **L1** | 悬液 `suspension` | 背景层 | 背景细胞、边缘裁切细胞、微尘微粒 | **0.34** | 是（仅 scale / alpha / 角度） | **否**——只有轮廓与内壁，无内部结构 |
| **L2** | 刻度 `reticle` | 背景层（仪器部分） | 测量网格、刻度标尺、标本编号、培养皿同心环 | **0.24**（文本用 `COL_FAINT` 实色，不算 alpha） | 否 | **是**，但必须弱于内容层 |
| **L3** | 舞台 `stage` | 舞台层 | 展台凹陷面（`COL_STAGE`，不透明）+ 展台内部的悬液与暗角 | 面 1.0；内部元素同 L1 | 是 | 部分（展台内 3 个细胞有动效） |
| **L4** | 内容 `content` | 内容层 | 卡片、按钮、文字、生命体、图表 | 不透明 | 内容自身动效 | **是，第一优先** |
| **L5** | 前景 `foreground` | 前景层 | 暗角、弹层遮罩、toast | **0.04**（压在内容上的部分）/ 0.16（不压内容的部分） | 否 | 否 |

绘制顺序（顶层在最后）：

```
ClearBackground(page_bg);    ← L0（主界面/Legacy = COL_BG；EoE = COL_BG_DEEP，见 §6.3 坑 4）
atm_draw_static();           ← L1+L2 静态（1 blit，满分辨率 Texture2D）
/* 全画布无实时元素；实时只在展台内，见下 */
draw_stage();                ← L3（内部再画一次局部悬液）
draw_top_bar / cards / ...   ← L4
atm_draw_vignette();         ← L5（仅最外 16px 环带，640×400 放大，1 次 blit）
draw_overlay();              ← L5 之上（弹层遮罩 + 面板）
```

> 注意 L3 的位置：展台是**内容层的一部分**（它是 `COL_STAGE` 不透明面），但它内部要画悬液，所以 `atm_draw_live` 必须提供一个"可传矩形"的版本（`atm_draw_live_in(Rectangle)`），让展台在填完底色后再调一次。传矩形只是**供落点计算用**（决定母题画在哪、弧取哪一段），**不是用来裁剪的**——`BeginScissorMode` 在本工程的 SS 架构下会错位，见 §0.3 B4。

### 1.2 铁律：背景层的对比度上限

> **铁律（硬，可测，唯一一条）**
> **任何背景像素，相对它所在底色（`COL_BG` / `COL_CHROME` / `COL_STAGE` / `COL_SURFACE_OFF`）的对比度 `CR ≤ 1.25`。**

> **判据只认最终合成色的 CR；单个元素的 α 是用来算的，不是用来判的。**
>
> 这一条是**项目级不可协商项**（与 §2.6.1 的 `α_min` 公式同批升格，2026-11-25 team-lead 确认）。它的意思是：任何人看到"我这个元素 α 才 0.22，肯定没超"就放行，都是在用**中间量**代替**结果量**。0.22 的 `COL_LINE` 叠在 0.60 的 `COL_CELL` 面上，合成后可能已经是 1.15——单看每个元素都合规，合起来越线。**没有例外，包括"两个都是合规元素"这种最像例外的例外。**

为什么要"相对底色"而不是"相对某个固定色"：背景元素散落在不同底色上（缝隙里是 `COL_BG`，展台里是 `COL_STAGE`，两者本身 CR=1.02），如果按固定色算，展台里的元素就会平白多出 1.02 的额度。

**工程换算（可直接写进代码的三个数）：**

| 数 | 值 | 含义 | 对应 CR（在 `COL_BG` / `COL_STAGE` 上实测） |
|---|---|---|---|
| 单元素 α 上限 | **0.30** | 一条 `Fade(COL_LINE, α)` 轮廓、或一个 `Fade(COL_CELL, α)` 填充 | 1.135 |
| 单像素累计 α 上限 | **0.34** | **同一个 token** 被 N 个背景元素叠到 | 1.158 |
| 硬天花板 | **0.489** | `Fade(COL_LINE, 0.489)` 恰好等于 CR 1.250，**这是禁越线** | 1.250 |
| 设计目标 | 近 0.30 / 中 0.22 / 远 0.14 | 三档景深 | 1.135 / 1.10 / 1.06 |

单元素 0.30 与单像素 0.34 之间留了 0.04 的余量，专门给"三条轮廓线交于一点"这种边角情况——1px 线的交点面积 < 4 px²，视觉上不可见，但不能让它在数学上破线。

> ⚠ **α 的可加性只对同一个颜色成立。** 一旦是"`COL_CELL` 面 + `COL_LINE` 环"这种**跨色叠加**，后叠的亮色会把底色重新拉高，α 不能相加、也不能按"各自都没超 0.30"来判。实测：

| 叠加方式 | 合成色 | CR（对 `COL_STAGE`） |
|---|---|---|
| 只有 `COL_LINE@0.30` | `#152427` | 1.135 |
| 只有 `COL_CELL@0.60` | `#0F1B1E` | 1.039 |
| **`COL_CELL@0.60` 上再叠 `COL_LINE@0.30`** | `#162528` | **1.154**（对 `COL_BG` 是 **1.166**） |
| `COL_CELL@1.00` 上再叠 `COL_LINE@0.30`（极端） | `#19282C` | 1.203 |

所以判据只认一条：**最终合成色相对底色的 CR**。上面这些"单元素值"是用来**算**的，不是用来的**判**的——与本节开头那条不可协商项是同一条规则，这里只是给它一组实测证据。

> **补充：跨色叠加的方向不是单调的。** 上表全是"亮色叠在暗面/暗色上 → 变亮"，容易让人以为跨色叠加**一定**往亮走。反例在 01 §4.4 注③：`main_line` 环 `Fade(COL_ACCENT, 0.35)` 落在 `1.08R @ 0.08` 的**同族光晕**上时，CR 从裸底 **2.29** 抬到 **2.56**——方向还是变亮，但增幅远小于"色差 × α"的朴素估算，因为两者色相接近、亮色先把底色推向自己。
>
> **判据永远是"算出来的合成色"，不是"看起来会变亮"。** 两个都合规的元素叠在一起，可能刚好越线（母题 A 的 1.166），也可能互相抵消一部分——**只有逐通道算一遍才知道是哪一种。**

### 1.3 为什么 1.25 不会破坏正文（实测，不是拍脑袋）

把底色抬到 CR 恰好 1.25（用 `COL_LINE` 在 `COL_STAGE` 上叠 α=0.489，得 `#1B2C2F`），然后算 01 §2.2 里每一级文字在这个"最坏底色"上的 CR：

> ⚠ **计算前提**：所有 alpha 合成都在 **8bit sRGB 码值空间**做线性插值（raylib `Fade()` 就是这样），合成完再线性化算 CR。**不能按亮度线性估算**——在暗底上这个错误会把可见度高估约 4 倍。详见 §2.6。

| 文字 token | 在 01 的 `COL_PANEL` 上（基准） | 在 CR=1.25 的最坏背景上 | 判定 |
|---|---|---|---|
| `COL_TEXT` #ECF4F1 | 15.08 | **13.03** | AAA 7:1 ✓✓ 余量 86% |
| `COL_DIM` #A3B8B6 | 8.10 | **7.00** | AAA 7:1 ✓ 余量 0% —— 卡在线上 |
| `COL_ACCENT` #35D6C6 | 9.31 | **8.04** | AAA ✓ |
| `COL_FAINT` #7A9392 | 5.15 | **4.45** | AA 4.5:1 ✗ **差 0.05** |

**这就是 1.25 的全部理由：它是 `COL_FAINT` 还能守住 WCAG AA 4.5:1 的最后一个值。** 再抬一点点（CR 1.28）`COL_FAINT` 就正式跌破 4.5，而 `COL_FAINT` 承载着全工程的单位后缀、快捷键、公式——它是"可以不读，但读了会更清楚"的那一级，不能失效。

两条配套推论，写进规范：

1. **`COL_FAINT` 文字绝不允许直接压在任何背景细胞上**。因此 §2.2 的避让区以**文字包围盒外扩 12px（`S_SAFE`）**为单位，而不是以卡片为单位——因为展台内的物种名（`COL_TEXT` 16px）和"主谱系"（`COL_ACCENT` 12px）是**直接坐在展台面上**的，那里没有任何卡片保护它们。
2. **施工值取 CR ≤ 1.20，验收线 1.25** —— 中间 0.05 是给实现误差的缓冲。为什么不是更小的 1.16：因为**跨色叠加时 α 不可加**（§1.2 的表里，"`COL_CELL@0.60` + `COL_LINE@0.30`"实测 1.166，而两个元素单独看只有 1.039 和 1.135）。1.166 就是本方案的实测最坏点，把它装进 1.20 有 2% 余量。任何一处量出 1.22 以上，说明有人把 α 写错了，应该回头查而不是调验收线。

### 1.4 一个必须先讲清的事实：背景只有 26.7% 能被看见

这是本文最重要的一条工程现实。主界面所有卡片都是**不透明**的（`COL_PANEL` α=255），所以背景层只有在"卡片之间的缝"里才存在。实测这些缝：

| 左边距 | (0, 100, 20, 624) | 12 480 |
| 右边距 | (1260, 100, 20, 624) | 12 480 |
| 左列与中列之间 | (380, 100, 16, 624) | 9 984 |
| 中列与右列之间 | (920, 100, 16, 624) | 9 984 |
| 左列内三条横缝 | (20, 330, 360, 32) | 11 520 |
| 中列内三条横缝 | (396, 154, 524, 40) | 20 960 |

三条由此得出的设计结论，直接决定了 §2 怎么写：

| # | 结论 | 后果 |
|---|---|---|
| C1 | 缝宽只有 **10–20 逻辑像素**，任何半径 > 20 的圆都必然被切掉一半以上 | **母题必须是"碎片可读"的**：一条弧 + 一道内壁环，就能让人读出"这是个大圆的一部分"。不要设计"完整的小细胞"，它在缝里永远只能露出一只手 |

**同时这也否决了一条看起来更省事的方案：让卡片半透明，把背景透出来。** 实测数据：

| 卡片不透明度 | 卡片底色（叠在 CR1.25 的背景细胞上） | vs 原 `COL_PANEL` 的差 | 结论 |
|---|---|---|---|
| α=1.00（现状） | `#121F22` | — | 基准 |
| α=0.96 | `#121F23` | 1 个色阶 | 肉眼看不出，白付一层混合成本 |
| α=0.88 | `#131F24` | 2 个色阶 | 仍然看不出"有细胞"，但已经开始让 12px 中文的底衬变得不匀 |
| α=0.78（要看出来至少得这样） | `#152026` | 4 个色阶 | **`COL_TEXT` 的 15.08 依赖底色恒定；底色一旦浮动，01 §2.2 整张 CR 表全部失效** |

**结论：卡片保持完全不透明。** 氛围不做在卡片里，只做在缝里、展台里、全屏页里。这不是偷懒，是因为"透出来的那点亮度差"在数学上根本不够被看见，只会换来一张无法维护的 CR 表。

**E 是本文的核心母题**，值得单独解释：圆心刻意放在画布**外面**（`c.x ∈ [−60,−24]` 或 `[W+24, W+60]`，`R ∈ [90, 220]`），画面上只出现一小段弧。它同时给了三件事：

1. 神秘感——你看不到全貌，只知道"它比视野大"；
2. 显微镜隐喻——视野是被裁切的圆形，不是无限世界；
3. **零成本**——1–2 个调用，且它只出现在边距 20px 里，绝不会碰到任何文字。

### 2.2 分布规则

#### 2.2.1 摆位：不是"随机撒"，而是"让弧穿过缝"（**必须用固定表**）

**先讲一条决定性的几何事实**：缝只有 10–20px 宽。如果一个圆的**圆心落在缝里**，你在缝里看到的是这个小圆的"腰部"——一个 16×60 的胶囊/竖条，**读不出圆**。只有当**圆弧本身穿过缝**（圆心在卡片后面或画布外，圆周恰好扫过缝）时，那 16px 才是一条有曲率的弧，才读得出"这里有个圆被挡住了"。

由此得到摆位铁律：

> **每个母题的可见片段必须包含"弧段"，不能只是"圆内部的一条"。**
> - **NEAR / MID（R ≥ 26）**：圆心必须放在**卡片后面或画布外**，圆周扫过缝；
> - **FAR（R ≤ 26）**：直径接近缝宽，圆心**可以**落在缝里，此时看到的是"被左右裁掉的小圆镜"，也成立。

**后果：不能用 hash 抖动生成位置。** 40 个 160×160 的格子里，真正能让弧穿过某条缝的落点占比很低；随机抖动几乎必然产出"缝里一条竖条"这种废品。所以：

| 做法 | 结论 |
|---|---|
| hash 抖动（v1.0 原方案） | ✗ **放弃**。命中率太低，且生成结果无法复核 |
| **固定坐标表（附录 D）** | ✓ **采用**。6 个母题的 `(cx, cy, R, 档位, 母题)` 已在本文件算好并逐点校验过：可见像素数、可见覆盖率、圆心两两间距、是否落在文字禁区 |

附录 D 的表已经过以下四项校验（脚本可复现）：

| 校验 | 结果 |
|---|---|
| 每个母题的可见像素 > 0 且包含弧段 | 6/6 ✓ |
| 圆心两两距离 ≥ 48px（§2.2.1 原约束） | 15 对全部 ≥ 136px ✓ |
| 可见面积总和 / 缝隙总面积 | **18.1%**（上限 40%）✓ |
| 可见片段是否触碰任何 `ui_text` 包围盒 | 全部不触碰 ✓ |

**绘制顺序**：仍按 `R` 降序（大的先画、小的压在上面）→ 产生"远的东西被近的挡住"的层叠感。

#### 2.2.2 密度上限（硬）

| 场景 | 母题数上限 | 说明 |
|---|---|---|
| 主界面缝隙 | **6** | 近 2 / 中 2 / 远 2（具体坐标见附录 D） |
| 展台内部（524×300） | **4** | 近 1（实时）/ 中 1（实时）/ 远 2（静态） |
| End of Era / Legacy 全屏页 | **12** | 面积大、无卡片遮挡，这里才是氛围红利最大的地方 |
| 弹层打开时 | **0**（背景不再重画） | 遮罩 α=0.72 会把背景压到 CR ≈ 1.0，画了也看不见，纯浪费 → 见 §6.1 |

**覆盖率**这条必须按**"可见片段面积"**算，不能按"标称圆面积"算——因为 NEAR 母题的圆心在画布外，标称面积 88 700 px² 里有 90% 根本不在屏上。按附录 D 的固定表实测：

| 量 | 值 |
|---|---|
| 6 个母题的**可见像素**合计 | **20 946 px²** |
| 缝隙总面积 | 115 904 px² |
| **可见覆盖率** | **18.1%**（上限 40% ✓） |

> v1.1 曾写"42 826 px² = 37%"，那是用标称圆面积算的（R=64/64/44/44/28/28），**口径错了**。换成弧穿缝的摆位后真实可见覆盖率只有 18.1%，比原来更"轻"，也留出了 22% 的余量给全屏页。
>
> 顺带回答一个可能的误传：**"每帧 24 个漂移细胞 + 40 粒微尘"不是本文的数字**（本文是 10 母题 / 6 微尘 / ≤16 调用）。
>
> 这里要说清一件事，避免有人以为我在用"调用数"去拦 24：**母题总数与每帧调用数无关**——所有静态母题都在 L1+L2 那一张 `Texture2D` 里，无论画面里有 6 个还是 60 个，每帧都只花 **1 次 blit**。所以 24 的真正代价不在调用预算，而在三处：
>
> 1. **覆盖率**：按每个母题平均 1 300 px² 可见面积估，24 个 ≈ 31 200 px² ≈ 缝隙面积的 **27%**（还在 40% 内，但已吃掉大半余量）；若这 64 个元素里有相当一部分是每帧实时的，才会撞调用上限。
> 2. **一次性预渲染调用**：从约 114 涨到约 200（一次性，可接受，但实现复杂度翻倍）。
> 3. **圆心距 ≥ 48 的硬约束**：缝只有 10–20px 宽，24 个圆要塞进这些窄条里，几乎必然出现两个圆共用同一段缝而圆心距不足，此时它们会挤成一个"椭圆团"，读不出"两只细胞"。
>
> **结论：10 / 6 / 16 是"能守住 40% 覆盖率 + 圆心距 + 每帧 1 blit"这三个约束的最大值，不是随手取的保守数。** 若将来要加，先按上面三条重算，再改数字。

### 2.3 景深模拟：raylib 没有模糊，怎么做出"失焦"

不要试图用 `DrawCircleV` + 大 alpha 做"模糊"——那只会得到一个硬边圆盘。**正确做法是"柔边 = 多层同心、逐层降 alpha、逐层外扩"**：

| 档 | R 范围 | 层数 | 每层的半径与 alpha | 内部结构 | CR 峰值 |
|---|---|---|---|---|---|
| **近** `NEAR` | 40–64 | **3** | `1.00R @0.30` / `1.06R @0.18` / `1.13R @0.09`（均 `Fade(COL_LINE,·)`） | 1 圈内壁（母题 A 的③） | 1.135 |
| **中** `MID` | 26–40 | **2** | `1.00R @0.22` / `1.08R @0.11` | 无 | 1.10 |
| **远** `FAR` | 12–26 | **1** | `1.00R @0.14` | 无 | 1.06 |

三条判据让"远 = 虚"成立，缺一条就变成"远 = 小"：

| # | 判据 | 为什么 |
|---|---|---|
| D1 | 远景**没有内部分区**（没有核、没有细胞器、没有内壁环） | 有内部结构 = 有焦点 = 读作"近"。这是唯一不需要模糊就能表达景深的手段 |
| D2 | 远景 alpha 更低 **且** 尺寸更小 **同时成立** | 只降 alpha = "褪色"；只缩尺寸 = "小东西"。两者同时 = "远" |
| D3 | 每档只有 1 条轮廓线，**不同时叠多层**（除了 NEAR 的 3 层柔边） | 层数越多，边缘越"糊"，但糊到一定程度就变"脏"（§4.4） |

**为什么用"外扩降 alpha"而不是"缩小降 alpha"**：外扩叠层时，圆心处的累计 alpha 最高、边缘最低，读起来是"中间实、边缘虚"——这正是失焦的光学特征（弥散圆）。如果反着做（大圆低 alpha 外套小圆高 alpha），会得到"亮环"，读作"发光"，违反 P1 的"光只从背后透"。

**一条硬拆分（保证 §6.1 的预算算得平）：实时绘制的一律只用 MID 档的层数（2 层）；NEAR 的 3 层柔边只允许出现在预渲染的静态元素里。** 理由：多层柔边是"一次性投入"，把它放进每帧循环等于用 5 个调用换 3% 的观感提升。于是实时细胞的实际调用是：近（母题 A 精简）= 3、中（母题 B）= 2、远 = 1。

### 2.6 两套可见性判据（全文最容易出错的一处）

**先记住一个事实：raylib 的 `Fade()` 是在 8bit sRGB 码值空间做线性插值，不是在线性亮度空间。** 所以凭直觉"按亮度比例估 alpha"会系统性高估可见度。量级：对同一个像素，按亮度线性估算会把 **(CR − 1)** 这个超额量高估约 **4.4 倍**（实测对照：`Fade(COL_SP0, 0.02)` 在 `COL_STAGE` 上，按亮度估算得 CR 1.11，实际只有 **1.025**）。暗底上这个误差最严重，因为 `COL_STAGE` 的 L 只有 0.0077。

本文 v1.0 初稿就栽在这里：微尘写了 `Fade(COL_CELL, 0.04→0.09)`，实测合成后与底色**逐通道完全相同**（码值差 0），等于一个调用画了空气。现已修正（见 §2.5、§6.5）。

| 元素尺度 | 判据 | 为什么 | 阈值 |
|---|---|---|---|
| **面**（≥ 16px，人眼当作"表面"看） | **CR ≥ 1.06** | CR 本就是为"大面积表面"定义的 | 远 1.06 / 中 1.10 / 近 1.135 |
| **点 / 线**（≤ 2px：微尘、发丝刻度） | **8bit 码值差 ≥ 3**（取 RGB 三通道最大差） | 1.5px 的点只有 2–5 个像素，`round()` 的量化误差会直接吃掉整个元素；此时 CR 完全失真 | ≥ 3 |

实测对照（全部叠在 `COL_STAGE` 上）：

| 组合 | 合成色 | 码值差 | CR | 一个 1.5px 的点看得见吗 |
|---|---|---|---|---|
| `Fade(COL_CELL, 0.04)` | `#0C171A` | **0** | 1.002 | **完全看不见**（8bit 逐通道相同） |
| `Fade(COL_CELL, 0.09)` | `#0C181B` | 1 | 1.006 | 看不见 |
| `Fade(COL_LINE, 0.08)` | `#0E1A1D` | **3** | 1.031 | 勉强，像一粒灰 |
| `Fade(COL_LINE, 0.10)` | `#0F1B1E` | 4 | 1.039 | 看得见，退在后面 ✓ |
| `Fade(COL_LINE, 0.16)` | `#111E21` | **7** | 1.065 | 清楚可辨的悬浮杂质 ✓ |
| `Fade(COL_LINE, 0.22)` | `#132023` | 9 | 1.094 | 已经"太清楚"了 |
| `Fade(COL_LINE, 0.30)` | `#152427` | 13 | 1.135 | 轮廓级别（面判据的上界） |

注意第 3 行：**CR 只有 1.031，远低于 §1.2 的 1.06 目标，但那个点确实看得见。** 这就是为什么微小元素不能用 CR 判——反过来说，裸 `COL_LINE` 在 α=0.08 时的 CR 比"远景细胞"（CR 1.06）还低，却更"存在"，因为前者是点、后者是面。

**推论——写进代码的五个常量：**

| 元素 | 允许区间 | 依据 |
|---|---|---|
| `COL_CELL` **面**填充 | **α ≥ 0.45**（常规取 0.55） | 0.45 差=3、0.55 差=4、0.75 差=5；**低于 0.45 差 ≤ 2，会被 `round()` 吃掉**。⚠ 特别注意 **0.40 这个值**：`0.40 × 7 = 2.8`，**卡在 3 与 2 个码值之间**，`round()` 给 3、`floor()`/`lrint()` 给 2 —— 属于"时有时无"的坑，换编译器、换 SSE 路径、甚至同一构建换个优化等级都可能翻面。**舍入相关的 bug 最贵，因为它复现不稳定**；这类"刚好卡在整数边界"的 α 一律往上取整到安全侧 |
| `COL_CELL` 柔边环 | **α ≥ 0.60**（母题 A 用 0.60，正好在下限） | 它是"面"的一部分，必须被看见才成立；同时它压在 fill(0.55) 上只差 1 个码值，正好"看不出接缝"——跨色叠加因此可控 |
| `COL_LINE` **轮廓线**（面级） | **0.14 – 0.30** | 下界 = 远档仍可见（CR 1.06）；上界 = §1.2 单元素上限 |
| `COL_LINE` **微尘**（点级） | **0.10 – 0.16** | 码值差 4–7；< 0.08 被量化吃掉，> 0.22 太清楚 |
| `COL_LINE` **网格线**（线级） | **0.16 – 0.22** | 线有长度，判据介于点与面之间 |

**一句话记法：面用 CR，点用码值差；跨色叠加一律回落到 CR（α 不可加）。** 中间尺度（3–15px）按点判据、取区间偏上限。

#### 2.6.1 下限的公式（不要背表，算出它）

> **2026-11-25 升格：`α_min = 3 / max|Δchan|` 现为项目级规则，不再只约束背景层。** 任何新增的背景元素、光晕、描边、分隔线、幽灵轮廓、图表辅助线，定 α 的第一步都是算 `max|Δchan|`，**而不是先画出来看**。理由不是公式算得准，而是它把"凭感觉定 α"这个动作彻底消灭了——不再需要问人、不再需要截图比对、不再会出现"PC 上看得见 / 某分辨率下看不见"。
>
> 落点：① **本文**（推导 + 三色对照表，见下）；② **`01-visual-identity.md` §4.4** ——**已完成，2026-11-25**：单层下限由固定值 `0.04 ≤ a ≤ 0.10` 改为本公式（`α × max|Δchan| ≥ 3`），`0.04` 保留在 §4.4 注②里作为"当年没有公式时的 2 倍保守值"，**标注为推荐值而非下限、不删**；同时修正了原来"0.02 在 `COL_STAGE` 上只产生 0.3–0.6 个码值"的错误依据（真实码值差是 **(1,3,2)**，G 通道差 3，恰好踩在阈值上）。

上面那些区间不是拍出来的，它们全部来自同一个式子。**由于 `Fade()` 在码值空间线性混合，叠 `α` 后的最大通道差就是 `α × max|Δchan|`。要让一个元素在 8bit 上活下来，要求这个值 ≥ 3：**

> **α_min = 3 / max|Δchan|**　（`Δchan` = 该颜色与底色的逐通道差）

三类元素实测验证（底都是 `COL_STAGE`）：

| 颜色 | 与 `COL_STAGE` 的 Δchan | `max\|Δchan\|` | 公式给出的 α_min | 实测吻合 |
|---|---|---|---|---|
| `COL_SP0`（物种绿） | (62, 153, 99) | 153 | **0.020** | α=0.02 → 差 3 ✓ |
| `COL_LINE` | (31, 42, 43) | 43 | **0.070** | α=0.08 → 差 3 ✓ |
| `COL_CELL` | (5, 7, 7) | **7** | **0.43** | α=0.40/0.45 → 差 3 ✓ |

**这个式子解释了两件看起来矛盾的事：**

1. **同一个 α，有的颜色看得见、有的看不见** —— 因为决定可见度的是"色差 × α"，不是 α。`COL_SP0` 在 α=0.02 就够，而 `COL_CELL` 要 0.43，两者差 20 倍，纯粹因为前者与底色差 153 个码值、后者只差 7 个。
2. **`COL_CELL` 被锁在 "CR vs `COL_BG` < 1.10" 之后仍然能用** —— 它作为 token 确实几乎等于底色（所以 α_min 高到 0.43），但它是给**大面积**用的，α 本来就在 0.45–0.60，正好越过下界。**这是刻意的分工，不是漏洞。**

反过来说，**给任何新元素定 α 之前，先算 `max|Δchan|`，再套公式**——不要再靠"看起来差不多"。

> 这条也解释了 §5.1 为什么把 `COL_CELL` 锁在 "CR vs `COL_BG` < 1.10" 之后还能用：**它作为 token 确实"几乎看不见"，但作为 α=0.55 的大面积面，差 4–5 个码值就够成立了。** 两个数字不矛盾，它们量的是不同的东西。

## 3. 生物科技感的三个具体承载

"科技感"这个词没法施工。下面三个东西可以。每个都附"为什么它读起来是生物实验室而不是科幻 HUD"。

### 3.1 极细测量网格（`RETICLE_GRID`）

| 参数 | 值 |
|---|---|
| 间距 | **32** 逻辑 px（4K 加强后从 64 收到 32，见 §6.4） |
| 线宽 | **1** 逻辑 px（`DrawLineEx`，`W_HAIRLINE`） |
| 颜色 | `Fade(COL_LINE, 0.16)` → CR **1.06**（肉眼几乎不可见，但和底色差一档；加强刻度 0.22 → CR 1.09） |
| 范围 | **只出现在舞台外的缝隙里**，以及**舞台的下 1/3**（`y ∈ [366, 466]`，最后 100px）。舞台中上部（生命体所在，`y ∈ [166, 366]`）**禁画** |
| 是否闭合 | **不追求闭合**。每 4 格断开 1 格（即从第 5 格线开始不画），形成断续的刻度带 |
| 加强刻度 | 每第 4 条线（128px）长度 +8px、α 提到 0.22 |
| 数量 | 水平 25 条 + 垂直 40 条 ≈ 65 条线 → **全部预渲染**，每帧 0 调用 |

**为什么是实验室不是 HUD**：科幻 HUD 的网格是全屏、强制正交、绝对闭合、平均加权的（它表达"我在一个坐标系统里"）。显微镜目镜的刻度是**局部、断续、贴边、有主次**的（它表达"我在一个有限的圆形视野里，只有边缘有刻度"）。**断续 + 不覆盖主体 + 主刻度加长**这三件事，就是实验室语法。

### 3.2 标本编号与刻度标尺（`SPECIMEN_LABEL`）

| 参数 | 值 |
|---|---|
| 内容 | 2–3 组，形如 `F12 / S.03`、`40×`、`B2-910`（B2-910 已存在于主界面「生物量里程碑」，直接复用其语法） |
| 字号 | **12**（`F_CAPTION`） |
| 颜色 | `COL_FAINT`（无需 alpha——它落在 `COL_BG` 上，CR 5.66，达标） |
| 位置 | 贴着舞台**左下角外** 8px、贴着「生物量里程碑」卡右侧 8px——**不对称、不在正中、不居中** |
| 数量 | 主界面 ≤ 3 处；全屏页 ≤ 5 处 |
| 内容合法性 | 只允许"编号 / 倍率 / 批次号"三种语法。**禁止写状态**（不能写"已解锁""待发现""最佳记录"——那是内容层的活） |

**为什么是实验室不是 HUD**：HUD 的文本是**状态**（HP 42/100、目标距离 320m），它必须实时可读、必须居中或对齐到网格。实验室的标签是**贴在玻片边上的标签纸**：编了号、走了一套人定的编码体系（F=field, S=slide, B=batch）、位置歪、字号小到只有凑近才读。**"编号而不是状态"这一条，是这两者最干净的区分。**

### 3.3 培养皿同心环（`PLATE_RING`）

| 参数 | 值 |
|---|---|
| 环数 | **3**，`0.970R / 1.000R / 1.035R`，`R` = 展台**半宽** = 262 |
| 线宽 | 1 / 1 / 1 逻辑 px；实现为 **`DrawRing(R − 0.5f, R + 0.5f, start, end, seg, col)`**，半宽**恒定 0.5f，任何 SS 下都不许改**（01 §4.5.2） |
| α | 0.14 / 0.20 / 0.10（`Fade(COL_LINE, ·)`） |
| **完整性** | **不闭合**，而且有双重理由：① 角度只画 `150°–210°` 与 `330°–30°` 两段（左右两侧）；② `R=262 > 展台半高 150`，环在上下方向必然长出展台，被裁掉 |
| 位置 | 圆心 = 展台中心 `(658, 316)`。可见结果：展台左右两侧各露出一段 3 条同心弧，上下完全为空——读作"皿沿从窗外探进来" |
| 裁剪 | **不用 `BeginScissorMode`**（SS>1 时裁剪矩形会被 Camera2D 的 zoom 重复放大 → 错位，见 §0.3 B4）。改为**按角度精确算出可见弧**：母题与展台矩形的交点反解出 `start/end` 角度，直接传给 `DrawRing(start, end)`，一个像素都不用裁 |
| 调用 | 每环 2 段 = 6 个 `DrawRing` → 预渲染，0/帧 |

**为什么是实验室不是 HUD**：HUD 的环是**完整同心**的（雷达、冷却、护盾），因为它的功能是"读满一圈"。器皿的环是**被遮挡、不闭合、有粗细变化**的，因为它表达的是"一个实体物件的边沿反光"。**不闭合**是关键——一个不闭合的环让人想到"这个圆有厚度、有一部分在阴影里"，一条完整的环只会让人想到"进度"。

> **⚠ 一条我发出过又撤回的错建议，留档防复犯**：我曾建议 `hw = (ss <= 1) ? 0.5f : 0.75f`，理由是"SS=1 时 1 逻辑 px 只有 1 个设备像素、零余量，怕浮点误差把环断成虚线"。**art-director 用 12 组配置 × SS=1/2/3 × 1440 个采样角（共 51 840 个采样点）实测否定了它：**
>
> | 项 | `±0.5f` | `±0.75f` |
> |---|---|---|
> | 断成虚线的角度数 | **0 / 51 840** | **0 / 51 840** |
> | 环宽实测（逻辑 px） | **1.00 / 1.00 / 1.00** | 1.50 / 1.53 / 1.50 |
> | SS=1 的宽度波动 Δ | 0.39–1.13 | 0.46–0.93（**没更稳**） |
>
> **根因：`DrawRing` 是填充环（三角扇），不是 GL 线段，根本没有"1px 发丝被浮点误差打断"这种失效模式。** 那个病属于 `DrawCircleLinesV`——上一轮刚把它从代码里赶出去。**同一个"细线"表象、两个不同成因，不能把 A 原语的病算到 B 原语头上。**
>
> 而且 `±0.75f` 有三重代价：① 环宽 1.5 **违反 01 §4.2「描边必须是整数逻辑像素」**；② 面积 +50%，皿环的 α 只有 0.10–0.20，体积一涨就会从"反光"变成"描边"；③ **按 SS 分档会让 SS=1 的窗口不再是 4K 的忠实预览**，而"SS=1 与 SS=3 视觉一致"是这套超采样架构唯一的正确性凭据——**唯一的 SS 分支必须留在 `ui_canvas_ss()` 里，任何绘制调用内都不许出现。**

## 4. 神秘感的三个承载

### 4.1 暗角（两级，位置不同、上限不同）

暗角必须分两级，因为"压在文字上"和"不压在文字上"的安全值差了 3 倍。

| 级 | 位置 | 环带宽 | 层数 | α 步进 | 累计 α | 实测影响 |
|---|---|---|---|---|---|---|
| **L1-V 背景暗角** | 在内容层**之下**（背景层里），画布四边 | 112 / 72 / 36 px | 3 | 0.030 / 0.035 / 0.040 | **0.101**（最外圈） | 只作用于缝隙与全屏页，**永不影响文字**，可全力发挥 |
| **L5-V 前景暗角** | 在内容层**之上** | 仅最外 **16** px | 1–2 | 0.020 / 0.020 | **0.040** | `COL_FAINT` 从 5.15 → **4.85**（仍 ≥ 4.5 ✓）；`COL_TEXT` 从 15.08 → 13.99 |

实现：每级 = 4 条边带 × N 层 `DrawRectangleRounded(rect, 0, 1, Fade(COL_VIGNETTE, α))`。3 层在四角自然叠成更深的角（这正是想要的"目镜"感），边带之间的接缝 α 差 = 0.005–0.03，**小于 01 §7.2 R6 的 0.04 上限，看不出台阶**。

> **L5 为什么只给 16px**：16px 恰好是顶栏 pill 左边距（20px）以内的环带，也是左右边距（20px）的主要部分；再往里就会开始压到「生命体」卡的 `x+16` 内边距（距左边 36px），那里的 12px `COL_FAINT`"空格"提示会掉到 4.85 以下。**16 是实测能守住的最后一个值。**

### 4.2 景深虚化（见 §2.3 的 D1–D3）

不重复。要点：**近 3 层 / 中 2 层 / 远 1 层 + 远景无内部结构**。成本全部落在预渲染里。

### 4.3 图鉴轮廓幽灵（**L4 内容层**，修复 01 的 D14）

01 §10 的 D14 说：未发现的 22/26px 头像位是"纯灰圆 + ?"，7 个节点完全同形，探索感为零。本文给出规格：

| 项 | 规格 |
|---|---|
| 画什么 | **该阶段模板的轮廓版**：只画 01 §5.2 阶段模板里那几条圆与环的**外沿**，内部全空。注意 `DrawCircleV` 是实心，所以"轮廓"必须用 `DrawRing(0.97R, 1.00R)` 这类极窄环来表达（`DrawCircleLinesV`/`DrawCircleLines` 不在 01 §5 允许的 7 个 API 里，**不得使用**） |
| S0（单细胞） | 1 × `DrawRing(0.97R, 1.00R)` = 1 调用 |
| S1（功能化） | 1 × `DrawRing(0.97R, 1.00R)` + 2 × `DrawRing(0.27R, 0.30R)`（伪足外沿）= 3 调用 |
| S2（群体） | 1 × `DrawRing(0.83R, 0.86R)` + 4 × `DrawRing(0.19R, 0.22R)`（卫星外沿）= 5 调用 |
| S3（器官化） | 2 × `DrawRing(0.97R, 1.00R)` / `(1.05R, 1.07R)` + 3 × `DrawCircleSector(0.86R, a₀, 55°, 24, Fade(COL_GHOST, 0.18))` 扇区残影（a₀ = 0/120/240）= 5 调用 |
| 颜色（图鉴，底 = `COL_SURFACE_OFF`） | `Fade(COL_GHOST, 0.65)` → 合成 `#18292C`，CR **1.18**、码值差 16（可见，但明显弱于已发现节点的 `COL_SP*` 6.27） |
| 颜色（进化树，底 = `COL_PANEL_HI`） | ⚠ **不能用 `COL_GHOST`**。`Fade(COL_GHOST, 0.65)` 在 `COL_PANEL_HI` 上合成 `#1D2F32`，**CR 只有 1.058、码值差 5** → 低于 01 §2.5 的同面阈值 1.10，轮廓直接消失。**改用 `Fade(COL_LINE, 0.55)`**（合成 `#23373B`，CR 1.184、码值差 13） |
| 图鉴文本 | 保留 `???`，12px `COL_FAINT`——**不要**因为有了轮廓就删掉 `???`（P3：静态可读，轮廓是"钩子"不是"答案"） |
| 成本 | 7 个节点 × 3–5 调用 = 21–35 调用；图鉴是弹层，**静态**，可整层预渲染 |

**为什么它给的是"神秘"而不是"信息"**：能认出"这是第 3 阶段的形态"（多卫星），但认不出"是哪个物种"（没有身份色）。玩家的推理链是"我知道它大概是什么级别的生物，但不知道是谁"——这个缺口正好是"想去解锁"的动力。给纯灰圆 + ? 则完全没有推理链。

### 4.4 为什么这些不等于"脏"

"脏"和"神秘"在像素层面的差别只有一条：**亮度变化是"有序下降"还是"无序上升"**。

| 做法 | 亮度变化方向 | 有序性 | 读作 |
|---|---|---|---|
| 暗角（3 层边带） | 沿离屏中心距离**单调下降** | 高度有序，只有 3 个台阶 | 神秘 ✓ |
| 景深（远 α 低 + 尺寸小 + 无内部） | 沿"深度"**单调下降** | 有序 | 神秘 ✓ |
| 轮廓幽灵（1px 线 + 0 填充） | 只有 1 个亮度层 | 有序 | 神秘 ✓ |
| 随机噪点贴图 / 脏色斑 / 高频纹理（**本文禁止**） | **随机上升**（局部亮点） | 无序 | 脏 ✗ |
| 给背景细胞加高光斑 / 加多重阴影 | **方向性上升** | 无序（且违反 P1） | 脏 ✗ |

三条可执行的判据：

1. **背景层只用 3 个亮度档**（对应 §2.3 的近/中/远）。第 4 档出现即为"脏"。
2. **背景层不引入任何新色相**。全部是 `COL_CELL`（H=191°）与 `COL_LINE`（H=189°）的不同 alpha，色相与 `COL_BG`（H=190°）完全同族。判据见 §5.3 F3：**色相必须落在 180°–200°**，出界即为 bug。
3. **背景层没有"细节"**。每个母题 ≤ 1 条内壁环。有 3 条以上内部结构的，会自动被眼睛读成"内容"，那就抢戏了。

## 5. 新增配色 token

### 5.1 背景层：2 个，都必须"几乎看不见"

约束（来自 01 §2.5 的反向利用）：**与 `COL_BG` 的 CR 必须 < 1.10**。含义是：这些色**单独铺满整个画面也看不出分层**，可见度 100% 来自 alpha 叠加。这样做的好处是——**即使某处 α 写超了，结局也只是"淡一点的同色"，不会出现一块抢戏的亮斑。**

> **但"< 1.10"只是上限，不是全部。** v1.1 起本文有了 §2.6.1 的下限公式，于是**背景 token 必须落在一个窗口里**：
>
> | | 判据 | 保证 |
> |---|---|---|
> | **上限** | `CR vs 底色 < 1.10` | 不抢戏（单独铺满也看不出分层） |
> | **下限** | `max\|Δchan\| ≥ 3 / α_max` | 能看见（给定 α 下的 8bit 存活线） |
>
> `COL_CELL` 的窗口是：`max|Δchan| ≥ 7`（α=0.45 时）**且** `CR < 1.10`。对着 `COL_STAGE` 它落在 7 **刚刚够**——**这就是它为什么必须占用 0.45 这么高的 α 下限、而不是像轮廓线那样 0.14 就够。**
>
> ⚠ **窗口很窄，动一下底色就可能关死。** 实例：若把 `COL_BG` 抬到 `#101E20`(16,30,32)，它与 `COL_CELL`(17,30,33) 只差 **Δ=(1,0,1)** → `max|Δchan| = 1` → **α_min = 3.0（数学上不可能）**，即"背景细胞"这个母题当场作废。而在保持青灰色相的前提下，同时在 `COL_BG` 与 `COL_STAGE` 两个底上都过窗口的候选**只剩 10 个**，最好的一个可见度也从 1.086 掉到 1.032、α_min 从 0.30 抬到 0.375（贴着两侧墙）。
>
> **结论：选背景 token 时，上限和下限要一起量。只查"< 1.10"会得到一堆看起来合格、实际画不出来的颜色。**

| 常量名 | hex | RGB | CR vs `COL_BG` | CR vs `COL_STAGE` | 用途 | 使用禁忌 |
|---|---|---|---|---|---|---|
| `COL_CELL` | `#111E21` | 17, 30, 33 | **1.086** ✓ | 1.068 | 背景细胞的**面**（填充、柔边）、培养皿内壁 | ① 不得用于内容层任何场合（卡片/按钮/文字底衬/分隔线）；② 不得单独承担可见性（单用 = 看不见，必须配 `Fade(COL_LINE,·)` 轮廓）；③ 不得用于 `COL_PANEL` 之上 |
| `COL_VIGNETTE` | `#050C0E` | 5, 12, 14 | **1.064** ✓ | 1.094 | 暗角（两级）、展台四角压暗 | ① 不得用于内容层；② 不得大面积平铺（仅限 ≤112px 的边带）；③ 不得替代 `COL_BG_DEEP`（那个是不透明的清屏色） |

### 5.2 内容层：1 个，**不受 1.10 约束**

`COL_GHOST` 属于 L4（图鉴未发现位），它是"内容"，必须能承载状态，所以要亮到能被看见。单独列出以免被 §5.1 的规则误伤。

| 常量名 | hex | RGB | CR vs `COL_SURFACE_OFF` | CR vs `COL_PANEL` | 用途 | 使用禁忌 |
|---|---|---|---|---|---|---|
| `COL_GHOST` | `#1E3134` | 30, 49, 52 | **1.31** | 1.24 | 图鉴未发现物种的轮廓线（`Fade(COL_GHOST, 0.65)` 后在 `COL_SURFACE_OFF` 上实测 **1.18**） | ① **只允许出现在 22/26px 头像位**；② 不得用于任何文字；③ 不得用于已发现节点（已发现必须用 `COL_SP0..6`）；④ **底为 `COL_PANEL_HI`（进化树非当前卡）时禁用**——CR 只有 1.06，轮廓会消失，改用 `Fade(COL_LINE, 0.55)`（见 §4.3） |

### 5.3 冻结规则（新增，加在 01 §2.5 之后）

| # | 规则 |
|---|---|
| F1 | `COL_CELL` / `COL_VIGNETTE` 与 `COL_BG` 的 CR 必须 < 1.10。任何人想调亮它们必须先改这条规则并重算 §1.3 的表 |
| F2 | 背景层**不新增第 4 个 token**。需要更亮的效果时，用 `Fade(COL_LINE, α)` 提 α，不要新增颜色——新颜色会带来新色相，新色相就是"脏"的入口 |
| F3 | 背景层的**色相族锁死**：任何背景元素（取色 + 叠色后的实际像素）的色相必须落在 **180°–200°**，且饱和度 **≤ 0.53**。实测：`COL_BG` H=190° / S=0.522，`COL_CELL` H=191° / S=0.485，`COL_LINE` H=189° / S=0.377 —— 三者是同一个灰青族，只是亮度不同。**反面例子**：`COL_ACCENT` H=174° / S=0.752、`COL_SP4`（粉）H=337°。任何一个出现在背景层，画面立刻从"培养液"变成"科幻 HUD 发光" |
| F4 | `COL_GHOST` 只属于 L4，`grep COL_GHOST` 的结果里不允许出现背景层函数名 |

> 3 个新 token 需要在 `ui_internal.h` 的 `extern` 块补齐声明（同 01 附录 B 的做法）。

## 6. 性能预算

### 6.1 每帧绘制调用预算

**判定基准**：01 §5.2 里最复杂的 S3 生命体约 **20** 个调用。背景层是"陪衬"，**不能比它更贵**。

| 项 | 预算 | 说明 |
|---|---|---|
| **背景层每帧硬上限** | **16 调用** | 超过即为实现错误，不是"优化建议" |
| 告警阈值 | 12 | 到 12 就开始查是不是有东西该预渲染 |
| S3 生命体（基准） | 20 | 背景层必须显著低于它 |

**16 的分配表：**

| 元素 | 调用/帧 | 备注 |
|---|---|---|
| L1+L2 静态层 blit | **1** | 满分辨率 `Texture2D`，`DrawTexturePro`（src 整张、dst 逻辑 `{0,0,1280,800}`）|
| L5 暗角 blit | **1** | **640×400** `Texture2D` 双线性放大，`DrawTexturePro` |
| 展台内实时细胞 A（近，母题 A） | 3 | fill + 柔边 + 内壁 |
| 展台内实时细胞 B（中，母题 B） | 2 | |
| 展台内实时细胞 C（远） | 1 | |
| 展台内微尘 | 6 | 6 × `DrawCircleV`，α 呼吸 |
| **合计** | **14** | 余量 2 |
| 弹层打开时 | **2** | 只保留两个 blit；`atm_draw_live*` 整体跳过（遮罩 α 0.72 下面看不见，见 §2.2.2） |

### 6.2 必须预渲染到 RenderTexture 的清单（一次性）

这些元素如果每帧重画，总调用会到 **120+**，是 S3 的 6 倍——直接违反"不能比 S3 更贵"。

| 元素 | 调用数 | 为什么必须预渲染 |
|---|---|---|
| 测量网格（水平 25 + 垂直 40） | 65 | 数量最多、完全静态 |
| 标本编号文本 | 3 | 静态、且文本绘制比圆贵 |
| 培养皿同心环（3 环 × 2 段） | 6 | 静态 |
| 边缘裁切细胞 E（4 个） | 8 | 静态 |
| 缝隙内母题（6 个 × 2–5） | 18 | 静态（其中 0 个需要动效） |
| L1-V 背景暗角（4 边 × 3 层） | 12 | 静态 |
| 展台内静态远景细胞（2 个） | 2 | 静态 |
| **小计（一次性）** | **≈ 114** | 只在 init / resize 时跑 |
| L5 前景暗角（4 边 × 2 层） | 8 | 单独一张 RT（它要盖在内容上，z 序不同） |

**验收判据**：`atm_draw_static` + `atm_draw_live` + `atm_draw_live_in` + `atm_draw_vignette` 四个函数体内的 `Draw*` 调用点合计 ≤ 16；两个 blit 各算 1。数法见 §7.2 A3（**不要为可测性在 release 热路径加计数**）。

### 6.3 显存规格（含三个会直接搞坏的坑）

> **v1.2 更正：本节 v1.1 写的"4K 氛围 RT = 35.2 MB"是错的，少算了一半。** raylib 5.5 的 `LoadRenderTexture()` 内部固定调用 `rlLoadTextureDepth(w, h, true)` —— **每条 RenderTexture 强制附带一个 32bit 深度 renderbuffer，无法关闭**。engineering-lead 用启动日志取证：每条 RT 成对出现 `Texture loaded (R8G8B8A8)` 与 `Depth renderbuffer loaded (32 bits)`；SS=1→3 实测工作集 146MB→230MB（+84MB）与此吻合。

| 项 | 计算 | SS=1 | SS=2 | SS=3（4K） |
|---|---|---|---|---|
| 颜色纹理 | W×H×4 | 3.9 MiB | 15.6 MiB | 35.16 MiB |
| 深度 renderbuffer（**强制**） | W×H×4 | 3.9 MiB | 15.6 MiB | **35.16 MiB** |
| **一条常驻 RT 合计** | | **7.8** | **31.3** | **70.3** |
| 主画布 RT（施工前已存在，不计入增量） | | 7.8 | 31.3 | 70.3 |
| ~~氛围层也用 RT 并常驻~~ | | 15.6 | 62.5 | **140.6 ✗** |

**所以不要长期持有 RT。** 静态层的本质是"一生只渲染一次"，用完立刻把 RT 换成一枚普通 `Texture2D`：

```
① rt = LoadRenderTexture(UI_W*SS, UI_H*SS)
② ClearBackground(page_bg)                  ← 契约 #1（不透明底，避免预乘偏色；且必须是**该页**底色，见坑 4）
③ 画完全部静态母题（约 114 个调用，只跑这一次）
④ Image img = LoadImageFromTexture(rt.texture)
⑤ ImageFlipVertical(&img)                    ← 坑 2，见下
⑥ UnloadRenderTexture(rt)                    ← 立刻还回 70.3 MiB 与深度缓冲
⑦ Texture2D tex = LoadTextureFromImage(img); UnloadImage(img)
```

**最终的常驻账：**

| 常驻项 | SS=1 | SS=2 | SS=3 |
|---|---|---|---|
| 主画布 RT（含深度，既有） | 7.8 | 31.3 | 70.3 |
| 静态氛围 `Texture2D`（满分辨率，**无深度**；**只持有当前页那一张**，见坑 4） | 3.9 | 15.6 | **35.16** |
| 暗角 `Texture2D`（**1/2 逻辑分辨率** = 640×400） | 1.0 | 1.0 | 1.0 |
| **氛围层自身增量** | **4.9** | **16.6** | **36.2 MiB**（≤ 40 MiB 上限 ✓） |
| 含主画布的总占用 | 12.7 | 47.9 | 106.5 |

**为什么暗角可以降到 1/2 逻辑分辨率（640×400），而静态层必须满分辨率：**

| 层 | 分辨率 | 理由 |
|---|---|---|
| L1+L2 静态（网格/刻度/皿环/母题/背景暗角） | **满分辨率** | 含 1 逻辑 px 的网格发丝线；降到 640×400 会把 1px 线放大成 3px 灰带，直接毁掉断言 A7 |
| **L5 前景暗角** | **640×400** | 它是**纯 3 台阶平滑渐变、零细节**。640→3840 的 6× 双线性放大反而把台阶磨得更顺，正好达成 §4.1「能数出台阶但看不出接缝」。边带 112/72/36 逻辑 px 降采样后仍有 56/36/18 texel，远大于表达 3 个台阶所需的最小宽度 |

> 降分辨率还有一个"副作用是好的"：L5-V 的 16px 环带在 RT 里只有 8 texel，放大后边界会软 ±2 逻辑 px —— 但那一层 α 只有 0.02–0.04，2px 的边界模糊看不出来，而省下的是 34 MiB。

**坑 1 —— premultiply 偏色（v1.1 起）**：RT 里若先 `ClearBackground(BLANK)`（透明）再画半透明内容，多层叠加后的 straight-alpha 结果整体 blit 会**偏暗**。

> **规避：RT 内部第一件事就是 `ClearBackground(page_bg)`，让 RT 成为不透明图。** 这样 blit 混合等价于直接画，还能省掉主循环一次清屏。
> 代价：**这张纹理从此绑定"某一个页面底色"，不能跨页复用。** 见坑 4。

**坑 2 —— RT 读回来是上下翻转的（v1.2 新增，漏做则整层倒置）**：raylib 的 RenderTexture 纹理在显存里是**垂直翻转**的（这正是 `DrawTextureRec(rt.texture, {0,0,w,-h})` 那个经典写法的由来）。一旦走 `LoadImageFromTexture` 转 `Texture2D`，拿到的 Image 也是翻转的。

> **规避：`LoadImageFromTexture` 之后必须 `ImageFlipVertical(&img)` 再 `LoadTextureFromImage`。** 漏掉这一步的后果是**整个背景层上下颠倒**——而它恰好不会被任何 CR 断言抓到（颜色全对，只是位置反了），只会在"网格怎么跑到上面去了"这种目检里暴露。建议把这条写进 `atmosphere.c` 的函数头注释。

> **这条比坑本身更值得留下——它是一条关于"验收方法"的教训：**
>
> **断言只能证明"颜色对"，证明不了"位置对"。**
>
> 我们这一轮的所有可测断言（A1 的 CR、A9 的码值差、A10 的 grep）全都在验证色值、计数、文本模式。它们**结构性地对位置失明**：一个整体翻转的背景层，A1 采样到的每个像素颜色都完美合规，A8 的 `COL_FAINT` 对比度照样 4.85，A3 的调用数一个不多。**唯一能抓住它的手段是"人看一眼"。**
>
> 所以 §7.2 的所有断言**不能构成完整验收**，必须配一次目检——而且目检要看的是**位置关系**（网格在下 1/3、暗角在四边、母题被卡片切掉一半），不是"好不好看"。这也解释了为什么 §7.1 要写成五句话的**具体描述**而不是"感觉对就行"：描述里每一句都含一个位置判据。

**坑 4 —— 静态层纹理绑定页底色，三页不能共用一张（v1.4 新增）**

坑 1 要求 RT 以**不透明底色**起手，那张纹理就"自带背景"。而三页的底色并不相同：

| 页 | 底色 | vs `COL_BG` 的 CR |
|---|---|---|
| 主界面 / Legacy | `COL_BG` #0B1517 | 1.000 |
| **End of Era** | `COL_BG_DEEP` #070E10 | **1.050** |
| （顶 / 底栏 `COL_CHROME` #0F1C1F） | 不含在静态层底面上 | 1.064 |

如果在 End of Era 页 blit 一张 `COL_BG` 底的静态层，**整页底色会被抬到 `COL_BG`**——EoE 与 Legacy 于是变成同一个颜色，"终止 vs 新起点"的语义差被抹平到 1.000。

> **规避（不增加常驻显存）：每页一张、切页重烧，同一时刻只持有当前页那一张。**
> - 常驻仍是 **36.2 MiB**（一张静态 + 一张暗角），**不破 40 MiB 上限**
> - 切页开销 = 一次 114–200 个调用 + 一张满分辨率**临时** RT（峰值瞬时 70.3 MiB，用完立刻卸载）
> - `atm_ensure(page_id, ss)` 的语义因此是"**这页的纹理 + 这个 SS 都对**才复用"，`page_id` 与 `ss` **任一变化都重烧**（与坑 3 同一条路径）

> ⚠ **这条差到底算不算"够"——2026-11-25 已由 01 §2.5 改判据回答，结果对我们有利。**
>
> 我原先按"CR ≥ 1.10 才是最小可见量"判它**不达标**，并建议把 `COL_BG_DEEP` 压深。**那个建议是错的，方向也反了**（压深会让文字 CR 升高、更安全，真正失去的是青色身份）。art-director 把 §2.5 改成双判据：中亮面（`L ≥ 0.01`）用 `CR ≥ 1.10`，**近黑面（`L < 0.01`）用亮度比 `L_hi / L_lo ≥ 1.4`**。
>
> 按新判据：`BG_DEEP` ↔ `BG` 的亮度比是 **1.69，远超 1.4 ✓ 达标**；而且它与另一对"视觉差一档"的 `COL_PANEL` → `COL_PANEL_HI`（CR 1.136 / 亮度比 **1.69**）是**同一个数**——两对视觉上确实同档，只是 CR 把它量成了 1.136 与 1.051。
>
> **根因**：`CR = (L_hi+0.05)/(L_lo+0.05)` 在 `L ≈ 0.005` 时，`+0.05` 占绝对主导，公式被硬拽向 1。**用 CR 判近黑面，等于用一把量程被截断的尺。** 而且 `CR(COL_BG, 纯黑) = 1.1339` 是它对任何更暗色的**理论上限**——1.10 在近黑区不是"严格"，是**不可达**。
>
> **所以我的责任边界很清楚，只有一条：不许把 1.05 抹平到 1.000。** 差够不够，是 01 §2.5 的事，那边已经判完了。

**坑 3 —— 窗口尺寸变了，SS 就变了，静态层必须重烧（预防性）**：静态 `Texture2D` 存的是**物理像素**（`UI_W*SS × UI_H*SS`）。用户按 F11 全屏或拖窗口边，`SS = clamp(ceil(min(winW/1280, winH/800)), 1, 3)` 可能从 3 掉到 2 或升到 3。此时旧纹理的尺寸与新 SS 不匹配，`DrawTexturePro` 会把它拉伸——**结果是网格线宽不再是 3 物理像素（A7 直接失效），而且不会有任何报错**。

> **规避：`atm_ensure()` 接受当前 SS 作为参数，与已持有的 `texSS` 比较，不等就"卸载旧 tex → 按 §6.3 流程重烧"。** 一次重烧约 114 个调用 + 一张满分辨率临时 RT，发生在 resize 事件里（不在帧循环里），可以接受。
> **注意别把 SS 存成全局并由绘制函数每帧读**——那是 §0.3 B2 明令禁止的；正确做法是 `ui.c` 在 resize 时算一次 SS，通过 `ui_backdrop_invalidate()` 通知，`atmosphere.c` 在下次 `atm_ensure()` 里取一次。

| 重建时机 | **仅在窗口 resize 且 SS 变化时重烧一次**，绝不每帧 |
|---|---|
| 重烧成本 | 4K 下 readback 约 30–60ms，开局一次，用户无感 |

### 6.4 4K 加强项（SS=3 之后，以前不能做的现在能做了）

ENG-01 落地 R8 之后（120px 字体图集 + SS=3 超采样画布），01 §7.3「本轮不做 R8」的建议已作废。以下是**现在可以做、以前不行**的具体项：

| # | 项目 | 以前（SS=1 时代）为什么不行 | 现在（SS=2/3） | 每项成本 |
|---|---|---|---|---|
| K1 | **发丝刻度线**用 1 逻辑 px | 1 逻辑 px = 1 texel，非整数倍下采样会让它一段粗一段细（01 §7.2 R1 的顾虑） | SS=3 时 1 逻辑 px = **3 texels**，粗细绝对均匀 → 可以放心用 1px 画背景刻度（**正文/控件描边仍守 01 §4.2 的 1 或 2**，不改） | **0**（已预渲染） |
| K2 | **网格间距 64 → 32** | 间距 32 时 1px 线之间只有 31px 空隙，SS=1 下线本身就虚，整个屏幕会糊成一片灰 | SS≥2 线实了，32px 网格读作"细密刻度"而不是"脏" | RT 内多 25 次 `DrawLineEx`（一次性） |
| K3 | **景深层数 3 → 5**（仅 NEAR 档） | 5 层 α 步进只有 0.03–0.04（01 §7.2 R6 的上限），SS=1 时每层的环边都太软，5 层叠起来是"一坨" | SS=3 时 5 个台阶各自清晰，边缘真正像弥散圆 | 每个近景母题 +2 调用（一次性，预渲染） |
| K4 | **环分段数 48 → 96**（R ≥ 80 的环） | 大半径下 48 段的多边形感可见（弦高 ≈ 0.1px，但 SS=1 时会被采样成锯齿） | 96 段，弦高 0.025px，在 4K 上是真圆 | `DrawRing` 的 segments **不增加 draw call**，只 +192 顶点/环 → 无感 |
| K5 | **1.5 逻辑 px 微尘点保留** | SS=1 时 1.5px 会被光栅化成 1 texel 硬点，看起来像坏点 | SS=3 时是 4.5 texel 的柔点，真的像悬浮微粒 | 0 |
| K6 | **卡片圆角缺口露出的背景弧**（§1.4-C2） | 12px 圆角的缺口只有 31px²，SS=1 时几乎看不见 | 4K 下那一点弧线能被看到，免费多一层景深线索 | **0**（本来就是背景漏出来的） |

**4K 加强项的三条禁令（本轮不做）：**

| 禁令 | 原因 | 替代方案 |
|---|---|---|
| 不用 shader 做真高斯模糊 | 破坏"零 shader"约束，且 4K 下全屏后处理带宽昂贵 | §2.3 同心圆多层（K3 的 5 层就是这个的极限） |
| 不用位图噪点/颗粒贴图 | 破坏"零位图"约束 | §2.5 的 6 个微尘点 |
| 不为 SS=1 单独维护一套背景参数 | 会导致两套参数长期漂移 | SS=1 档接受"背景稍淡"，因为 **01 §7.3 C3 已声明 1600×1000（SS≥2）才是最小保证窗口**，960×600 只保证可运行 |

### 6.5 顺手修掉一处与 01 §8.3 的冲突（现有代码）

`screens.c:319-326`（`draw_stage` 的"背景气泡"）：

```c
for (int i = 0; i < 18; ++i) {
    ...
    float speed = 12.0f + fmodf(seed * 11.0f, 18.0f);
    float y = r.y + r.height - fmodf(S->time * speed + seed * 40.0f, r.height - 40.0f);
    DrawCircleV((Vector2){ x, y }, 1.5f + fmodf(seed, 2.0f), Fade(COL_ACCENT, 0.10f));
}
```

两个问题：

| 问题 | 说明 |
|---|---|
| 违反 01 §8.3「无限平移循环」 | `y` 随 `S->time` 匀速上浮并循环，是标准的无限平移。虽在卡内无文字游走风险，但字面违规 |
| 成本 18 调用且色相不对 | 18 次 `DrawCircleV` 用掉实时预算的绝大部分；`COL_ACCENT`（H=174° / S=0.752）违反本文 §5.3 F3 的色相族锁定（必须 180°–200°）——它看起来是"发光",不是"培养液" |

**替换方案**（同时解决两个问题，且省 12 个调用）：18 个上浮气泡 → **6 个固定位置、α 呼吸的微尘**（**`Fade(COL_LINE, 0.10 → 0.16)`**，周期 3.1s，半径 1.5px 固定）。位置由 `hash(i)` 一次性算好写死在静态 RT 里，每帧只做 6 次 `DrawCircleV` 改 α。

> ⚠ **不要用 `Fade(COL_CELL,·)` 画微尘**。本文 v1.0 初稿在这里写错过，实测已纠正：`COL_CELL`(17,30,33) 与 `COL_STAGE`(12,23,26) 的通道差只有 (5,7,7)，乘 0.04 后码值差为 **(0,0,0)** —— 8bit 四舍五入后与底色**完全相同**，画了等于没画。原因见 §2.6：`COL_CELL` 的设计前提是"几乎等于 `COL_BG`"，它只在大面积 + 高 α 时才成立。微尘必须用 `COL_LINE`（通道差 31/42/43，余量足够）。

### A.1 展台内 6 颗微尘的固定坐标（**必须用表，不许按 `i` 均匀分布**）

```c

static const Vector2 ATM_DUST_POS[6] = {
```

## 附录 Z｜Z-UNSAFE 原语白名单（实测，非估算）

> **收录说明（v1.3）**：本附录是 SS 缩放的**实测**结论，晚于 §0.3 B5 的初稿。B5 与 §7.2 A10 已按它**收窄**——B5 现在只约束背景层、判据改成"是否走 `glLineWidth`"，不再写成"禁止一切 `*Lines`"的通用禁令。两处如仍有不一致，**以本附录的实测表为准**，并请回报修正 B5。

> **为什么值得单独立个名。** SS 超采样架构（`LoadRenderTexture(W*SS, H*SS)` + `Camera2D.zoom = SS`）能让一切几何按 `SS` 倍放大——除了走 `rlBegin(RL_LINES)` 的那批。它们在 4K 上**还是 1 物理像素**，也就是比设计意图细 3 倍。
>
> **它 FAIL 得极其隐蔽**：线还在、颜色对、位置对，只是比旁边那条细了 2/3。在 SS=1 的开发窗口里完全正常，只有 A7 类断言（"1 逻辑 px 的线 = 3 物理像素"）能抓住。任何新人第一次画"一圈细线环"就会中招。

### Z.1 判据不是"函数名带 Lines"

raylib 画线只有两条路径：

| 路径 | raylib 内部 | 顶点变换 | 是否吃 `Camera2D.zoom` |
|---|---|---|---|
| 四边形 | `rlBegin(RL_QUADS)`，一条线展开成 4 个顶点 | CPU 端乘 `zoom` 后再送 GPU | ✅ 是（宽度 = `lineThick × zoom`） |
| GL 线段 | `rlBegin(RL_LINES)` + `glLineWidth()` | 只变换两个端点 | ❌ 否（宽度以**设备像素**计，与 zoom 无关） |

**决定性事实：raylib 在 `lineThick == 1.0f` 时会走第二条路径**（发丝线快路径），`lineThick ≥ 2` 才回到四边形。所以：

> 判据 = **这条线最终是不是由 `glLineWidth` 画出来的**，而不是函数名里有没有 `Lines`。
> 两个反直觉的推论：① `DrawRectangleLinesEx` 名字带 Lines 却**安全**；② `DrawRectangleRoundedLinesEx` **只是 `lineThick == 1.0f` 时才坏**，传 2 就完全正常。

### Z.2 实测表

**量法**（可复现）：`LoadRenderTexture(640×SS, 768×SS)` + `Camera2D{{0,0},{0,0},0,SS}` + `BeginMode2D`，每个原语单独占一行、**只留一道干净的水平笔画**（圆形/多边形把旋转调到让被测边水平，避免扫线穿过顶点），`ExportImage` 出 PNG 后**竖直扫一列、数满强度像素个数**。
**双跑判据**：真正不吃 zoom 的原语，在 **SS=2 和 SS=3 下都是 1**；跟随 zoom 的原语则分别等于 2 和 3。只跑一个 SS 会漏判——这会骗过只看"结果是不是 1"的人。

**安全（跟随 zoom）**

| 原语 | 调用参数 | SS=2 | SS=3 | 备注 |
|---|---|---|---|---|
| `DrawLineEx` | `w = 1` | 2 | 3 | 完全线性 |
| `DrawLineEx` | `w = 2` | 4 | 6 | 完全线性 |
| `DrawRectangleLinesEx` | `thick = 1` | 2 | 3 | **证伪了"它委派给 rounded 版本"的猜测** |
| `DrawPolyLinesEx` | `thick = 1` | 2 | 3 | **订正：上一轮曾误判为 Z-UNSAFE，见 Z.7** |
| `DrawRectangleRoundedLinesEx` | `thick ∈ (1.0, 1.1666]` | 2 | 3 | 有悬崖，见 Z.4 |
| `DrawRing`（填充环） | `r 11→12` | 8 | 12 | 厚度 4 逻辑 px ✓ |
| `DrawCircleV` / `DrawCircleSector` / `DrawRectangle` / `DrawRectangleRounded` / `DrawEllipse` / `DrawTriangle` / `DrawPoly` | 填充 | ×SS | ×SS | 顶点全部走 CPU 变换 |

**Z-UNSAFE（SS=2 与 SS=3 都是 1 设备像素）**

| 原语 | SS=2 | SS=3 | 触发条件 |
|---|---|---|---|
| `DrawLineV` | 1 | 1 | 恒 |
| `DrawLineStrip` | 1 | 1 | 恒 |
| `DrawRectangleRoundedLines`（3 参数版） | 1 | 1 | 恒（内部固定 thickness=1） |
| `DrawRectangleRoundedLinesEx` | 1 | 1 | **当且仅当 `lineThick == 1.0f`** |
| `DrawCircleLines` / `DrawCircleLinesV` | 1 | 1 | 恒 |
| `DrawEllipseLines` | 1 | 1 | 恒 |
| `DrawRingLines` | 1 | 1 | 恒 |
| `DrawCircleSectorLines` | 1 | 1 | 恒 |
| `DrawTriangleLines` | 1 | 1 | 恒 |
| `DrawPolyLines`（无厚度参数） | 1 | 1 | 恒 |

> 注意 `DrawPolyLines` 与 `DrawPolyLinesEx` 分属两张表：前者没有厚度参数、恒走 GL 线段；后者有厚度参数、恒走四边形。**这一对是最容易记反的。**

### Z.3 安全替代写法

| 想画 | 不要用 | 改成 | 备注 |
|---|---|---|---|
| 任意直线 | `DrawLineV` / `DrawLineStrip` | `DrawLineEx(a, b, W_HAIRLINE, c)` | 折线 = 逐段 `DrawLineEx`（≤8 段成本可忽略） |
| 细圆环 | `DrawCircleLinesV` / `DrawCircleSectorLines` / `DrawRingLines` | `DrawRing(c, R−w/2, R+w/2, a0, a1, seg, col)` | `DrawRing` 是唯一同时满足"能按角度裁切"和"能跟随缩放"的原语 |
| 细椭圆环 | `DrawEllipseLines` | 正圆走 `DrawRing`；非正圆用两枚 `DrawEllipse` 填充相减（填充安全） | raylib 没有椭圆环的安全版本 |
| 细三角环 | `DrawTriangleLines` | 三条 `DrawLineEx` 拼 | |
| 细多边形环 | `DrawPolyLines` | `DrawPolyLinesEx(..., 1.0f, ...)`，或 N 条 `DrawLineEx` | `Ex` 版安全 |
| 圆角矩形描边 | `DrawRectangleRoundedLines`（3 参数版） | **01 §4.5.1 方案 A（嵌套填充；原为附录 C 的实现备注，已升格为正式条款）**；半透明面应急可传 `1.05f`，见 Z.4 | |

### Z.4 `DrawRectangleRoundedLinesEx` 的 thickness 悬崖（可一行止血）

实测同一矩形在 SS=1/2/3 下改变 thickness，描边满强度像素数：

| thickness | SS=1 | SS=2 | SS=3 | 判定 |
|---|---|---|---|---|
| **1.0**（`W_HAIRLINE` 的现值） | 1 | **1** | **1** | ❌ 掉进 hairline 分支 |
| 1.05 | 1 | 2 | 3 | ✅ **全部正确** |
| 1.10 | 1 | 2 | 3 | ✅ |
| 1.1666 | 1 | 2 | 3 | ✅ 边界 |
| 1.17 | 1 | 2 | **4** | ⚠ 过冲 |
| 2.0 | 1 | 4 | 6 | 按 `thick × SS` 正常放大（不该用于发丝线） |

**结论：`thickness ∈ (1.0, 1.1666]` 是一段连续且完全正确的窗口，推荐钉在 `1.05f`。**

- 几何上描边落在矩形**外侧**恰好 1 逻辑 px（实测偏移 SS=3 时 `y ∈ [−3, −1]` 设备 px），**无缝、无重叠**——不同于 01 方案 A 的"内侧嵌套"，版面上会宽出 1px。
- ⚠ **但它是止血，不是替代方案。** 它依赖 raylib 内部 `== 1.0f` 这个分支细节，raylib 升级会**静默失效**（失效后表现为又变回 1 物理像素）。01 **§4.5.1 方案 A**（`ui_panel` 圆角描边改"外圈铺描边色 + 内缩 `W_HAIRLINE` 铺填充"的嵌套填充）是 API 语义层面的做法，不受版本影响，**仍是正式解**；`1.05f` 只用于"来不及重构、且必须让 A7 过"的调用点，并**必须写注释说明原因**。

**Z.5.1 一个被"回退路径 0 调用点"的结论漏掉的可达调用**

### Z.7 一处自我订正（写进来防止后面有人重犯）

上一轮我把 `DrawPolyLinesEx` 判成了 Z-UNSAFE（读到 1 设备像素）。**那是量法错误**：扫线恰好穿过多边形的顶点，顶点处笔画在扫描方向上只有一个像素。把旋转改成让被测边**轴对齐**后，得 SS=2 → 2、SS=3 → 3，**它一直是安全的**。
**教训：任何"数像素宽度"的断言，必须保证扫线垂直到一条边、不穿过顶点或尖角。** 这也是本附录坚持每次双 SS 跑的原因——`1` 这个读数既可能是"真不吃 zoom"，也可能是"扫到尖角了"，只有 `SS=2 → 2, SS=3 → 3` 这种成对读数才是安全的证据。

**复现材料**：`z5.c`（16 个原语 × SS=1/2/3）、`z6.c`（thickness 扫描）、`crop.py`（纯 Python PNG 解码 + 列剖面）。本文不含任何目检结论。
